# HLSL сбор шейдеров и декомпиляция AMD, Intel ISA

Набор скриптов для поиска шейдеров на гитхабе, анализа лицензий,
компиляции и дизассемблирования в ISA для AMD и Intel GPU. 

## Требования 
### Системные требования:
- **Python** 3.9+
- **Git**
- **DirectX Shader Compilers**: FXC and DXC
- **GPU Analysis Tools**:
  - AMD RGA (Radeon GPU Analyzer)
  - Intel Shader Analyzer

### Python зависимости:

-  `PyGithub`
- `scancode-toolkit`

## Этапы 
1. Получения списка репозиториев 
2. Клонирование 
3. Поиск лицензий
4. Вычисление базовой информации о файлах
5. Список файлов, фильтрация
6. Препроцессинг и поиск параметров компиляции
7. Компиляция 
8. Декомпиляция
9. Экспорт
> 2 и 3 происходят одновременно, 9 может быть до 8. Пометки "Время" - относительные, по опыту на списке выбранных лицензий.

### 1. Получение списка репозиториев 
> Время: быстро

На гитхабе запрашиваются репозитории по тегу `language:` предоставленному в **config**. На выбор предоставляются 3 варианта списков:
1. Все найденные репозитории
2. Топ 1000 репозиториев по звездам 
3. Поиск с тегами `license:` лицензий из **config**

Во всех вариантах, кроме второго, поиск разбивается на запросы по периодам, вплоть до поиска по дням, чтобы избегать лимитов гитхаба на выдачу по одному запросу. Меньше дней бить нельзя, но для hlsl это не проблема. 

### 2. Клонирование
> Время: ? 

Делается пустой клон, запрашивается список файлов, далее подгружаются 

- Файлы расширений **config.target_file_extensions**
- Файлы расширений **config.additional_file_extensions**
- Файлы с именами, которые детекция гитхаба приняла бы за лицензии, а именно по паттернам из этого [файла](https://github.com/licensee/licensee/blob/main/lib/licensee/project_files/license_file.rb).

> Также автоматически клонируются все файлы из корня репозитория, не стал это убирать. 

### 3. Поиск лицензий 
> Время: очень долго, даже со встроенной многопоточкой. 12+ часов?

В репозитории запускается `scancode`. Он для каждого файла ищет есть ли в нем лицензия, является ли он юридическим файлом (в противоположность коду). 

Далее при каждом запуске скрипт проходится по структуре репозитория и для каждого файла ищет лицензии, в следующем порядке:
1. Внутри файла 
2. В соседнем юридическом файле
3. В юридическом файле выше по иерархии папок, по близости к исходному файлу.

Сохраняются все лицензии первого найденного уровня.

### 4. Вычисление базовой информации о файлах
> Время: Долго, порядка 3-6 часов? 

Вычисляются 
1. Хэш
2. Является ли шейдером (по расширению файла)
3. Размер
4. Количество строк (без пустых)
5. Оценка принадлежности к целевым платформам (ReShade, Unity, UnrealEngine, Ogre3D, MS FX). У всех кроме MS FX есть внешние зависимости, что делает их непригодными к компиляции, у MS FX свой пайплайн и типы файлов.
6. Оценка принадлежности к 3м типам шейдеров (Pixel, Vertex, Compute)
7. Инклюды.
> Оценка целовой платформы в тч наследуется из инклюдов, если они были склонированы. 
> Инклюды ищутся вне зависимости от регистра, некоторые репозитории это предполагают, тк Windows. 
> Также учитываются прагмы для cpp/не cpp кода при поиске инклюдов. 

Далее отдельным проходом вычисляется **тип лицензии**, в тч если её нет или несколько валидных источников. Scancode для файлов где лицензия была
найдена выдает формулировку/название, смотрю просто что она из одного слова и соотвествует предоставленным в **config**.
Также считается **худшая лицензия среди инклюдов** (нет инклюдов < permissive < gpl < ... < файл не найден), тк она явно должна распространятся на 
скомпилированный файл.

### 5. Список файлов, фильтрация 
> Время: быстро

Фильтры: 
1. Однозначно определяется источник лицензии 
2. Были вычислены данные из п.4
3. Шейдер
4. Размер больше данного
5. Число строк больше данного
6. Уникальный хэш
7. Не в репозиториях из черных списков

Эти файлы войдут в базовый эскпорт. Далее для компиляции дополнительно остаются файлы 
1. Без найденных целевых платформ 
2. С лицензиями Permissive/GPL, и у самого файла, и у инклюдов. 

### 6. Препроцессинг и поиск параметров компиляции
> Время: долго, часов 3-6?

Для поиска входных точек и compilation target файлы подвергаются препроцессингу,
чтобы раскрыть макросы, убрать комментарии и тп. Препроцессинг делается и fxc, и dxc 
для всех файлов. Дополнительные директивны подтягиваются из **config** как написано выше. 

Далее для каждого обнаруженного типа шейдера проводится поиск входных точек и целевых профилей(compilation target).

### 7. Компиляция
> Время: долго, часов 6-7? 

В зависимости от обнаруженной compilation target файлы после препроцессинга компилируются fxc 
или dxc. Если известен тип шейдера, то при неизвестных compilation target просто перебираются до первого успеха. 
Если ничего не компилируется, результаты последней попытки для каждого варианта comptarget будут
записаны в meta.json, иначе только успешная компиляция. Для шейдеров модели 6.0 и выше также перебираются 
теги `-HV`. В случае если ни одна из типовых попыток не принесла результата, или если у файла не был определен тип,
осуществляется компиляция под `lib` профилем, просто чтобы заверить валидность кода. 

При успешной компиляции под типовым (не `lib`) профилем 6.0 и выше дополнительно осуществляется компиляция в spir-v,  
при этом перебираются `-fspv-target-env` от `vulkan1.0` до `vulkan1.3` и пробуются варианты 
`-fvk-use-dx-layout` и `-fvk-use-gl-layout` (и без обоих). 

Успешно скомпилированные хотя бы раз файлы помечаются как таковые в базовом экспорте. 

### 8. Декомпиляция 
> Время: Очень, очень долго. Около 40 часов. 
> Можно было распараллелить и ускорить в 2-3 раза, но тогда у меня на сутки компьютер был бы занят только этим, так что я не стал. 

Шейдеры модели 3.0 (dx9) и ниже не декомпилируются. Это потребовало бы совсем старых 
замороженных утилит, и вероятно не представляет большой ценности.

Для шейдеров модели 5.1 и выше, т.е dx12, требуется корневая сигнатура.
Возможно какие-то репозитории её предоставляют, но в подавляющем большинстве её нет. К примеру, больше половины шейдеров 
из набора собраны из трех репозиториев renodx, и там эти сигнатуры видимо как-то должен предоставлять движок. 
Это ограничение обходится компиляцией в spir-v, при которой, видимо, эти значения заполняются как-то дефолтно. 
Этот подход не работает напрямую для модели 5.1, тк она компилируется еще fxc, который делать spir-v не умеет. Технически 
есть способ переводить dxbc -> spir-v, но это еще один уровень абстракции над железом, и таких шейдеров в наборе ~50, так что 
делать его я не стал. То есть 5.1 тоже можно сказать не обрабатываются. 

Шейдеры скомпилированные под `lib` тоже не обрабатываются. Этот режим изначально создан для рейтрейсинга, и без 
специфичного для него синтаксиса декомпилирован не будет. Таких файлов в наборе (почти?) нет, поэтому компиляция в него используется просто для верификации валидности библиотечного (набор функций) файла.


В случае отсутствия целевых архитектур в **config** декомпиляция осуществляется для всех доступных. 
#### AMD: 
Используется Radeon GPU Analyzer. 

Для шейдеров 4.0 - 5.0 в режиме dx11, 5.1(6.0) и выше - vk-spv-offline для обработки spir-v.

#### Intel:
Используется Intel Shader Analyzer.

Для шейдеров 4.0-5.0 работает, для более поздних нет, поддержка инструмента была завершена. 

Intel в целом отошел от поддержки оффлайн-декомпиляторов, и теперь подход - ловить фреймы из работающих приложений, что в 
данном формате сбора датасета нерационально. Я некоторое время поискал пути обхода этого момента, но судя по всему сколько-нибудь 
адекватной поддержки нужного процесса для графических шейдеров нет. Поэтому шейдеры 6.0 и выше не обрабатываются.

### 9. Экспорт 
> Время: относительно быстро, до часа.

Экспорт осуществляется в архивы, все файлы названы по их хэшу и в базовом экспорте находятся по папкам 
с их лицензиями, как по тз. В экспорте ISA делать этого не стал, там файлы просто помечены по худшему типу лицензий 
себя и инклюдов, то есть просто Permissive/GPL. Базовая информация по файлам также не предоставляется, можно по хэшу посмотреть в табличке из базового. 

Вместе с экспортом ISA из файлов после препроцессинга убираются #line директивы. Иногда это не получается сделать, 
тк компиляторы, видимо, не всегда выдают валидный utf-8, так что будут писаться ошибки вида "Failed on ...". При записи непосредственно 
архива будут показываться ошибки про запись дубликатов, возникает на файлах у которых несколько входных точек. 
Ни на что не влияет, не стал исправлять.
